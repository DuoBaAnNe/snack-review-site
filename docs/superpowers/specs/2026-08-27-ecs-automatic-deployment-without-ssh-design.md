# 阿里云 ECS 无 SSH 自动发布设计

日期：2026-08-27  
状态：用户已确认  
触发方式：用户对 Codex 说“上线阿里云”

## 背景

`linglingqi.fun` 的中国内地流量已经由阿里云 DNS 指向深圳 ECS，境外和默认线路继续使用 Vercel。当前 ECS 发布流程已经支持指定 Git 提交、生产构建、原子切换、健康检查和失败回滚。

此前更新需要临时开放安全组 TCP 22、上传 Git bundle、登录服务器执行发布，再删除临时规则。ECS 访问 GitHub 还存在连接超时，因此不能把稳定发布建立在 ECS 主动拉取 GitHub 上。

用户已经删除临时 SSH 安全组规则。后续要求：

- TCP 22 长期关闭，不再为普通发布修改安全组。
- 用户只需说“上线阿里云”，由 Codex 完成发布和验证。
- 普通更新只发布到阿里云 ECS。
- Vercel 仅在用户明确要求重大版本上线时更新。

## 方案比较

### 方案 A：OSS 制品 + 云助手固定命令（选定）

本地测试通过后，把指定提交制作成发布制品并上传到私有 OSS；阿里云云助手在 ECS 内执行预先安装的固定发布入口，下载制品并调用现有发布流程。

优点：无需开放 22；不依赖 ECS 访问 GitHub；可限制到单台实例、固定命令和固定 OSS 路径；能够保留现有回滚和健康检查。

代价：需要一次性配置私有 OSS、ECS 实例 RAM 角色、云助手命令和本地发布身份。

### 方案 B：GitHub Actions 自动发布

推送代码后，由 GitHub Actions 上传制品并调用阿里云接口。

优点：完全无人值守。

缺点：每次提交都可能误发布；需要在 GitHub 保存阿里云权限；与“普通更新只上 ECS、重大更新才上 Vercel”的人为发布边界不够匹配。

### 方案 C：阿里云控制台手动执行云助手

用户在控制台上传制品并点击执行。

优点：不需要本地自动化凭据。

缺点：每次仍有多步人工操作，容易选错制品或实例，不满足“一句话上线”。

## 选定架构

```text
用户说“上线阿里云”
          │
          ▼
Codex 本地发布工具
  1. 检查工作区与目标提交
  2. 运行测试和生产构建验证
  3. 生成带 SHA-256 校验值的 Git bundle
          │
          ▼
阿里云私有 OSS（cn-shenzhen，临时发布制品）
          │
          ▼
阿里云云助手（限定实例 + 固定发布命令）
          │
          ▼
ECS 实例 RAM 角色下载制品
          │
          ▼
校验 → 构建 → 原子切换 → 健康检查 → 失败自动回滚
          │
          ▼
Codex 验证公网 HTTPS 与部署 SHA，并报告结果
```

公网入站只需要 80 和 443。云助手通过阿里云实例管理通道工作，不依赖公网 SSH 入站规则。

## 一次性配置

### 私有 OSS

- 在 `cn-shenzhen` 建立专用私有 Bucket，或在现有私有 Bucket 中建立专用发布前缀。
- 发布对象采用不可变路径，例如 `ecs-releases/<full-git-sha>/source.bundle`。
- 同目录保存校验文件 `source.bundle.sha256`。
- 禁止公共读、公共写和目录列举。
- 成功发布后删除本次临时对象；若删除失败则记录警告，并由生命周期规则兜底清理旧对象。

### ECS 实例 RAM 角色

- 给目标 ECS 绑定实例 RAM 角色。
- 该角色只允许读取专用 Bucket/前缀，不允许写入、删除或读取其他对象。
- ECS 下载制品时使用实例角色的临时凭证，不在服务器文件、仓库或命令参数中保存长期 AccessKey。

### 本地发布身份

- 使用单独的 RAM 用户或短期角色，不使用阿里云主账号 AccessKey。
- 权限仅包含：向专用 OSS 前缀上传/删除制品；查看目标实例和云助手执行结果；在指定实例上调用指定的固定部署命令。
- 凭据存放在阿里云 CLI 的本地安全配置中，不写入 `.env`、Git、日志或聊天。
- 条件允许时启用 MFA、定期轮换凭据，并优先升级为短期凭证。

### 云助手

- 确认目标实例上的云助手 Agent 正常。
- 创建一个固定、版本化的发布命令；普通发布身份仅能调用该命令，不能随意执行任意 root Shell。
- 固定命令只接受严格格式的 40 位小写 Git SHA 和匹配的 OSS 对象位置。
- 发布脚本放在 root 所有、普通用户不可写的目录中。

## 本地发布流程

用户说“上线阿里云”后，发布工具执行：

1. 确认目标项目、分支和 ECS 实例，显示将要发布的完整 Git SHA。
2. 拒绝发布未提交的修改；先保留用户工作区，不自动提交或丢弃文件。
3. 运行与风险相称的测试、生产构建和部署资产测试。
4. 为精确提交创建 Git bundle，不使用 `latest` 或移动分支作为服务器输入。
5. 计算 SHA-256，并将 bundle 和校验文件上传到私有 OSS 的不可变路径。
6. 调用固定云助手命令，参数只包含目标 SHA 和受限对象路径。
7. 等待并读取云助手执行状态；部署仍运行时持续等待，不重复触发。
8. 成功后从公网验证 `https://linglingqi.fun/api/health` 返回相同完整 SHA，并检查首页 HTTPS。
9. 删除 OSS 临时制品。
10. 报告部署 SHA、测试结果、云助手结果、健康检查结果和是否发生回滚。

该流程不执行 `git push`、`vercel deploy` 或 Vercel Promote，因此不会更新 Vercel。

## ECS 发布入口

新增明确的离线发布入口，替代之前临时创建的 wrapper：

1. 从专用 OSS 路径下载 bundle 和 SHA-256 文件到 root 专用临时目录。
2. 拒绝符号链接、异常文件类型、宽松权限和格式不正确的 SHA。
3. 在导入前验证文件 SHA-256。
4. 验证 bundle 内存在目标提交，并且 `ecs-release-<sha>` 标签精确指向该提交。
5. 把对象导入 `/opt/linglingqi/repository.git`。
6. 调用共享部署核心，继续执行依赖安装、测试、构建、原子切换、服务重启和健康检查。
7. 无论成功或失败都删除下载临时目录。

现有 `deploy.sh` 的在线 GitHub 发布仍可保留为受控维护手段，但日常自动发布不调用它。公共构建、切换和回滚逻辑应抽成共享脚本，避免在线与离线流程产生不同结果。

## 并发与幂等

- 继续使用现有 root 所有的 `flock` 部署锁，同一时间只允许一个发布。
- 如果目标 SHA 已经健康运行，发布入口返回“已是当前版本”，不重复构建。
- 如果目标 release 目录已存在但不是当前健康版本，拒绝覆盖并要求人工检查。
- 每个 SHA 使用唯一 OSS 路径；禁止覆盖已经上传的对象。
- 本地超时不等于服务器失败。超时后先查询同一次云助手 Invocation 状态，不创建第二次发布。

## 失败处理和回滚

- 本地测试或构建失败：不上传、不触发 ECS。
- OSS 上传或校验失败：删除不完整制品，不触发 ECS。
- 云助手不可用：不开放 22 作为自动回退；报告阻塞状态，网站继续运行旧版本。
- ECS 下载或校验失败：不修改当前版本。
- ECS 构建失败：不切换当前版本。
- 切换后健康检查失败：恢复上一版本并验证上一版本健康。
- 公网健康检查与本机结果不一致：停止清理诊断信息，不修改 DNS，不自动发布 Vercel。
- 回滚也无法恢复健康时：明确报告需要人工介入；仍不自动开放 22 或改安全组。

## 安全边界

- 安全组长期不开放 TCP 22；保持 TCP 80/443 公网访问，3000 仅监听回环地址。
- 自动化不得创建、修改或删除安全组规则。
- 不允许主账号 AccessKey，不允许把凭据传入聊天或提交 Git。
- 云助手调用权限限定到目标实例和固定命令，避免自动化获得任意 root 命令能力。
- ECS 只取得 OSS 只读临时权限；本地发布身份不能读取网站生产环境文件。
- 日志不输出 OSS 临时凭证、环境变量、数据库令牌、Cookie 或用户数据。
- 发布制品必须同时通过 SHA-256 和 Git 提交/标签校验。

## Vercel 发布边界

- “上线阿里云”：只调用本设计的 ECS 发布流程。
- “重大更新上线 Vercel”或用户明确同意：才单独执行 Vercel 发布流程。
- ECS 与 Vercel 允许在一段时间内运行不同代码版本，但继续共享 Turso 数据库；数据库结构变更必须向后兼容两个版本。
- 如果某次更新包含不兼容的数据迁移、环境变量变化或 API 契约变化，自动发布必须停止并提示需要联合发布或迁移方案。

## 测试

### 自动测试

- 参数校验：拒绝非完整 SHA、路径穿越和非预期 OSS 前缀。
- 制品校验：错误 checksum、缺少标签或标签与提交不一致时失败。
- 幂等测试：重复发布当前 SHA 不重建。
- 并发测试：第二个发布无法绕过部署锁。
- 回滚测试：模拟新版本健康检查失败，恢复上一 SHA。
- 边界测试：本地 ECS 发布命令中不存在 Vercel CLI、Git push 或安全组修改。

### 首次真实演练

1. 保持 22 关闭。
2. 发布一个无业务差异的测试提交。
3. 验证云助手执行、OSS 清理、本机健康和公网健康。
4. 再演练一次故意失败的构建或健康检查，确认旧版本仍在线。
5. 检查安全组没有新增规则，Vercel 生产版本没有变化。

## 验收标准

- 用户只需说“上线阿里云”即可完成发布。
- 整个过程不开放或使用 TCP 22。
- ECS 无需访问 GitHub。
- 只允许指定发布身份、指定命令、指定实例和指定 OSS 前缀。
- 目标 SHA 在本地、制品、ECS 和公网健康接口中一致。
- 失败发布不会替换健康的当前版本；切换后失败能够自动回滚。
- 普通阿里云发布不会触发 Vercel 更新。
- 临时制品和临时凭证不会残留或出现在日志中。
